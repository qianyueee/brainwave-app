# NeuroSync Windows アプリ／BrainLink ブリッジ（PC用）

BrainLink Pro ヘッドセットの脳波データを Bluetooth シリアル経由で読み取る
PC 側プログラム群です。用途は3通り：

- **A. Windows アプリ（NeuroSync.exe）** — Web 版と**同じ画面一式**（ホーム・Sync Session・
  Sync Brain・Sync Report・Sync History・設定）の PC アプリ。Sync Brain は **PC 単体で**
  BrainLink を読むので、ブリッジもスマホも要りません。ログインすると、測定・振り返り・
  再生の記録などが**アカウントで Web 版・Android アプリと揃います**。→「Windows アプリ」へ
- **B. 配布版ブリッジ（BrainLinkBridge.exe、Windows、Python不要）** — 従来方式。
  脳波をクラウドへ中継し、**スマホの Web アプリで見る**。→「配布版ブリッジ」へ
- **C. コマンドライン版（開発・検証用）** — Python が必要。→「コマンドライン版」へ

```
A: BrainLink ──Bluetooth──> NeuroSync.exe（読取・解析・表示・保存を1プロセスで。画面は Web 版と同じ）
                              └─（任意・既定OFF）クラウド同時配信 ──> 別の端末の Sync Brain
B: BrainLink ──Bluetooth──> BrainLinkBridge.exe ──インターネット──> スマホの Sync Brain
```

> **測る・見るだけならアカウントは不要です。** スマホへのリアルタイム中継（B と A の
> クラウド同時配信）は、両者が同じ**ペアリングコード**（スマホの Sync Brain「接続する」に
> 表示）を使うことだけが条件で、ログインの有無は関係ありません。
> A の記録を**アカウントに残して、ほかの端末でも見たい**ときだけログインします
> （ホーム右上の「ログイン」または設定。メール＋パスワード、または Google）。

## Windows アプリ（NeuroSync.exe）

以前の「デスクトップ測定アプリ（NeuroSyncMeasure.exe）」の後継です。測定だけの画面
だったものが、Web 版と同じ画面一式になりました。

### 旧版（NeuroSyncMeasure.exe）からの移行

1. 新しい `NeuroSync.exe` を、**古い `NeuroSyncMeasure.exe` と同じフォルダ**に置く。
   PC に残した記録とログイン状態はそのフォルダの `profile/` にあり、同じフォルダで
   起動すると引き継がれます。
2. 古い exe を閉じてから、新しい exe を起動する（2つ同時には起動できません）。
   動作を確かめたら、古い exe は消してかまいません。
3. ログインすると、古いアプリで測ってまだアカウントに保存していない測定があれば、
   ホームで「このアカウントに保存しますか？」と一度だけ尋ねます。

別のフォルダに置いた場合でも、アカウントに保存済みの記録はログインすれば戻ります
（PC にだけあった記録が見えなくなります）。

### 使い方

1. ヘッドセットの電源を入れ、PC とペアリング（→ 下の「Bluetooth ペアリングと
   シリアルポートの確認」）。
2. `NeuroSync.exe` をダブルクリック（未署名のため SmartScreen が警告したら
   「詳細情報」→「実行」）。ホームが開きます。
3. メニュー（左上）→ **Sync Brain** → **接続する** → BrainLink のポートを選んで
   **このポートに接続する**。
4. **測定を開始** で測定。終了するとまとめとメモ入力が出て、「脳特性チャートに
   取り込みますか？」と尋ねます（Web 版・Android アプリと同じ）。**取り込む**と
   アカウントに保存され、Sync Report・Sync History と、ほかの端末でも見られます
   （ログインが必要）。**あとで**を選んだ測定はこの PC にだけ残ります。測定の生データは
   いつも `logs/` の CSV に残ります。

- 実機が無いときは接続設定の「**合成データでテストする**」で、実機と同じ経路
  （解析→表示→CSV→クラウド）を合成データで確認できます。合成データの10秒チェックは
  「デモ」として扱われ、アカウントには保存されません。測定は「取り込む」とほかの測定と
  同じくアカウントに入るので、テストで測ったものは「あとで」で閉じてください。
- **クラウド同時配信（既定 OFF）**: 接続設定にスマホの Sync Brain「接続する」で
  表示されるペアリングコードを入力して「配信を開始する」を押すと、従来どおり
  スマホでも同じ測定をリアルタイムに見られます。コードは記憶しますが、配信の
  ON は起動のたびに入れ直します（起動しただけで黙って外に送り続けない）。
- プログラムの再生・書き出しも Web 版と同じです。曲（伴奏）はインターネットから
  読み込みます（初めて鳴らすときに通信が要ります。つながらなければ伴奏が無いだけで、
  誘導のビートは鳴ります）。書き出しは「名前を付けて保存」で保存先を選びます。
- 文字が小さいときは **Ctrl＋マウスホイール**（タッチパネルならピンチ）で拡大できます。

### ログインと、端末をまたいだ記録

ホーム右上の **ログイン**（または設定）から、Web 版と同じアカウントでログインします。

- **メール＋パスワード**：その場で入力。
- **Google**：「Googleでログイン」を押すと**いつものブラウザ**が開くので、そこで
  ログインします（Google はアプリ内の画面でのログインを受け付けないため）。終わると
  ブラウザに「ログインが完了しました」と出るので、タブを閉じてアプリに戻ります。

ログイン中は、次の記録がアカウントに保存され、Web 版・Android アプリ・ほかの PC と
同じになります：取り込んだ測定・10秒チェック・その日の振り返り・再生の記録・
感コンディション・測定者・マイ星座・Sync Tree。

- ネットが切れていても使えます。保存していない分は PC に残り、つながると自動で
  送られます。
- ログインする前に書いた振り返り・再生の記録・取った10秒チェックは、ログイン後に
  「このアカウントに保存しますか？」と尋ねます。共用の PC で別の人の記録が混ざらない
  よう、黙っては送りません。「保存しない」を選んだ記録はこの PC にだけ残ります。
- 測定者の名前をほかの端末と同じにしておくと、同じ人の記録としてまとまります。
- ログアウトはこの PC だけ（スマホや他の PC のログインはそのまま）。ログアウトすると、
  そのアカウントの記録はこの PC から見えなくなります（アカウントには残ります）。
  共用の PC では使い終わったらログアウトしてください。

**管理者向けの準備（初回のみ）**

1. Supabase の SQL Editor で `supabase/migrations/` の 003（測定・10秒チェック）・
   004（Sync Tree）・005（振り返り・再生の記録などの小さな記録）を、まだのものだけ
   番号順に実行し、続けて Web 版をデプロイする（各ファイルの冒頭コメント参照）。
2. Supabase → Authentication → URL Configuration → **Redirect URLs** に
   `http://127.0.0.1:17860/auth/callback` を追加する（Google ログインの戻り先）。
3. exe は GitHub Actions でビルドする（下の「ビルド」。リポジトリ変数
   `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` が Web 版と共通で
   使われ、無いとビルドが止まる）。

### 必要環境・作られるファイル

- Windows 10/11 と **Microsoft Edge WebView2 ランタイム**（通常はプリインストール。
  無ければ起動時に案内が出ます: https://developer.microsoft.com/microsoft-edge/webview2/ ）
- インターネット（ログイン・同期・曲の読み込み。測定そのものは無くてもできる）
- exe と同じフォルダに作られるもの：
  - `desktop_config.json` … ポート・コードなどの設定（`bridge_config.json` とは別）
  - `profile/` … 画面内の保存データ（記録・測定者・ログイン状態など。消すとアカウントへ
    送っていない記録も消える。フォルダを移すときは exe と一緒に）
  - `logs/session_*.csv` … 測定の生データ（従来ブリッジと同形式、下の「CSV ログの列」）
  - `neurosync_desktop.log` … 動作ログ

### ビルド（GitHub Actions）

**Actions** タブ → **Build Windows App** → **Run workflow**
（または `desktop-v2.0.0` のようなタグを push）。Windows アプリまわりを変えた push でも
自動で走り、exe を作ったうえで、サーバだけのモード（`--no-window --demo`）で起動して
画面とローカル WS が答えるかを確かめます（`smoke_desktop.py`）。成果物は
`NeuroSync-windows`、タグビルドは Releases にも添付。中では Web バンドル
（`pnpm build:desktop` → `bridge/web/`）→ PyInstaller（`NeuroSync.spec`）の順に
ビルドされます。

### 開発（ソースから実行）

```bash
# リポジトリ直下
pnpm install && pnpm build:desktop        # 同梱 UI を生成（bridge/web/。ソース実行では out/ を配る）
cd bridge
pip install -r requirements-desktop.txt
python desktop_app.py                     # ウィンドウ起動（Windows）
python desktop_app.py --no-window --demo  # サーバのみ + 合成データ（Linux/Mac 検証用）
python smoke_desktop.py --platform desktop  # 起動確認（上のサーバを立てた別のターミナルで）
```

`--no-window` のときは `NEXT_PUBLIC_APP_PLATFORM=desktop pnpm dev` を立てて
http://localhost:3000/ から繋げます（UI の変更が即座に反映される）。ローカル待受は
`http://127.0.0.1:17860`（画面・Google ログインの戻り `/auth/callback`）と
`ws://127.0.0.1:17861`（データ＋制御、プロトコルは `local_server.py` のコメントが正）。
**HTTP のポートは固定**です——画面内の保存データ（localStorage）は「アドレス＋ポート」
単位で隔離されるため、ポートが変わると記録が全部見えなくなります（Google ログインの
戻り先もこのポート）。WS のポートは空いていなければずれるので、最初に開くページの
`?ws=`（例 `http://127.0.0.1:17860/?ws=17861`）で画面に渡し、画面が覚えます。
WS は 127.0.0.1 / localhost のページからしか繋げません。
ログインを試すには、`.env.local` に Web 版と同じ `NEXT_PUBLIC_SUPABASE_URL` /
`NEXT_PUBLIC_SUPABASE_ANON_KEY` を置いてから `pnpm dev`（または `pnpm build:desktop`）。

> GitHub Pages 版のサイトにも `/desktop`（旧い測定アプリの画面）は存在しますが、
> リンクはどこにも無く、開いても `ws://127.0.0.1` に繋がらないだけで無害です。

## 配布版ブリッジ（BrainLinkBridge.exe、Windows、Python不要）

### 入手とビルド

ビルド済みの `BrainLinkBridge.exe` は GitHub Actions で作成します
（Linux/Mac では Windows用exeを作れないため、クラウドのWindows環境で自動ビルド）。

1. GitHub リポジトリの **Actions** タブ → **Build Bridge (Windows)** →
   **Run workflow** を実行（または `bridge-v1.0` のようなタグを push）。
2. 完了後、その実行結果の **Artifacts** から `BrainLinkBridge-windows`（zip）を
   ダウンロードし、展開すると `BrainLinkBridge.exe` が出てきます。
   （`bridge-v*` タグで実行した場合は Releases にも添付されます。）

### 使い方（利用者）

1. ヘッドセットの電源を入れ、PC とペアリング（→ 下の「シリアルポートの確認」）。
2. スマホでアプリの **Sync Brain**（脳波同期・測定）を開き、「**接続する**」を
   押すと表示される**ペアリングコード**（例: `AB23-CD45`）を確認。
3. `BrainLinkBridge.exe` をダブルクリック。
4. 画面に入力：
   - **ペアリングコード**: 手順2のコード
   - **BrainLink ポート**: ドロップダウンから選択（「更新」で再検索）
   - **詳細設定（クラウド接続）**: Supabase URL と anon key（既定値が入っています。
     通常は変更不要）
5. **測定を開始** を押す。「シリアル接続：接続」「クラウド接続：接続」が緑になり、
   集中/リラックスの数値が動き出せば成功です。スマホ側に脳波が表示されます。

> 実機がなくても、**「デモモード」**にチェックを入れて開始すれば、合成データで
> クラウド経路（スマホ表示）だけを先に確認できます。

設定は exe と同じフォルダの `bridge_config.json` に、測定データは `logs/` フォルダの
CSV に自動保存されます。

> ⚠️ 配布された exe は署名されていないため、Windows SmartScreen が警告を出す
> ことがあります。「詳細情報」→「実行」で起動できます。

## コマンドライン版（開発・検証用）

## 必要なもの

- BrainLink Pro ヘッドセット
- Python 3.10 以上が入った PC（Windows / macOS / Linux）
- スマホアプリに表示されるペアリングコード（アカウント不要）

## 1. Bluetooth ペアリングとシリアルポートの確認

ヘッドセットの電源を入れ、PC とペアリングしてください。
ペアリングすると「シリアルポート」として認識されます。

- **Windows**: 設定 → Bluetooth → その他の Bluetooth オプション → 「COM ポート」タブで
  `BrainLink` の **発信（Outgoing）** ポート（例: `COM3`）を確認
- **macOS**: ターミナルで `ls /dev/cu.*` を実行し、`/dev/cu.BrainLink_Pro` のような名前を確認
- **Linux**: `sudo rfcomm bind 0 <デバイスのMACアドレス>` で `/dev/rfcomm0` を作成

## 2. インストール

```bash
cd bridge
pip install -r requirements.txt
```

## 3. 設定

`.env.example` をコピーして `.env` を作成し、各項目を入力します。

```bash
cp .env.example .env
```

- `SUPABASE_URL` / `SUPABASE_ANON_KEY`: 既定値が同梱されているので通常は変更不要
- `PAIRING_CODE`: スマホアプリの Sync Brain「接続する」に表示されるコード
  （`--code AB23-CD45` のように実行時に渡すことも可能）
- `EEG_PORT`: 手順1で確認したシリアルポート

## 4. 動作確認（3ステップ）

いきなり本番ではなく、以下の順で1つずつ確認すると問題の切り分けが簡単です。

### ステップ A: クラウド経路の確認（実機不要）

```bash
python main.py --demo
```

合成データがクラウドに送信されます。スマホで Web アプリの Sync Brain を開き、
「接続する」を押してリアルタイムに切り替えると、そのダイアログに
**「ブリッジ：オンライン」** と表示され、光る点が動けば成功です。

### ステップ B: 実機の確認（クラウド不要）

```bash
python main.py --dry-run
```

ヘッドセットを装着して、コンソールに「集中 / リラックス」の数値が
流れれば成功です。データは `bridge/logs/session_*.csv` にも保存されます。

### ステップ C: 本番

```bash
python main.py
```

ヘッドセット → PC → クラウド → スマホ、の全経路が繋がります。
測定データは毎回 CSV にも自動保存されます。

## CSV ログの列

`logs/session_YYYYmmdd_HHMMSS.csv` は帯域パケット 1 つにつき 1 行（約 1 秒間隔）。

| 列 | 意味 |
|---|---|
| `ts` | PC の壁時計（epoch ミリ秒） |
| `attention` / `meditation` | eSense 集中度・リラックス度（0-100） |
| `delta` … `highGamma` | TGAM が出す 8 帯域パワー（無次元の生値。機種間で桁が違うので、比率にしてから使うこと） |
| `signal` | POOR_SIGNAL。0 = 接触良好、200 = 頭皮に触れていない |
| `battery` | 電池残量。実機のパーサは今のところこの値を出さないので、デモモード以外では空 |
| `rawPerSec` | 前の帯域パケットからこの行までに届いた raw 波形サンプル数（瞬間値） |
| `specRate` | そのスペクトルの周波数軸を作るのに実際に使ったレート（`rawPerSec` の移動中央値）。空欄＝レートが不明か範囲外で、スペクトルを出していない |
| `skipRows` | パーサが読まずに通り過ぎた行の内訳 `<コード>/<長さ>:<回数>`（1バイト行は長さなし）。通常は空欄 |
| `parseErr` | フレーミングの失敗回数 `chk`（チェックサム不一致→再同期）/ `trunc`（行がペイロードより長いと主張＝そのパケットの残りを損失）/ `plen`（ありえない長さバイト）。通常は空欄 |
| `spectrum` | その秒の 1〜64Hz 毎の FFT 振幅を `;` 区切りで並べたもの（先頭が 1Hz） |

### raw のレートと周波数軸

`_spectrum` は窓を「時間」ではなく「サンプル数」（512 個）で切るので、**周波数軸は
その 512 個がどれだけの速さで届いたかで決まります**。ここを 512Hz 固定だと決め打つ
のは誤りでした——実測すると、あるヘッドセットは帯域パケットあたりきっちり 512 個、
別のヘッドセットは一貫して 481 個しか送ってきません。後者を 512 として扱うと
**すべての周波数が 6.4% 高く出ます**（真の 40Hz のピークが 42.6Hz に描かれる）。
Bluetooth の取りこぼしでも同じことが起きます（バイト欠落 0.2% で 10Hz の α が
11Hz、2% で 15Hz）。

そこで基底はその都度**実測レート**（`specRate`）で作ります。レートが確定していない
起動直後や、値が 256〜560 の範囲を外れたときは**スペクトルを出しません**——ラベルを
付けられない軸を描くくらいなら、グラフが無いほうがましです。そのため:

- 各測定の最初の数行は `spectrum` が空（レートの中央値がまだ取れていない）
- `specRate` が測定中ずっと安定していれば、その回の Hz 軸は信用してよい
- `specRate` が測定中に動いた行は、Bluetooth の状態が変わっている

### サンプルが足りないときに、その理由を見る

`rawPerSec` が 512 に届かない場合、`skipRows` と `parseErr` がその内訳を示します。

- **両方とも空欄なのに足りない** … バイトがそもそも届いていない（Bluetooth の
  取りこぼし）。ヘッドセットとの距離・他の 2.4GHz 機器・PC の負荷を疑う
- **`parseErr` に `chk` が並ぶ** … 同上。欠落でバッファがずれ、偽の同期ヘッダを
  拾っている
- **`skipRows` に定常的な項目がある** … そのヘッドセットは、こちらが読んでいない
  行を毎秒その回数だけ送っている。キーが RAW のコード（`80/...`）なら、
  **捨てているのは波形そのもの**なので、その行を読めるようにすれば足りない分は
  戻る。私有の行（`ba/...` など）なら無害
- **`parseErr` に `trunc` が並ぶ** … 行の長さの解釈が合っておらず、そのパケットの
  残りを毎回失っている

実測では、あるヘッドセットが 481 raw/s しか出さず、その不足が 19.68Hz とその
高調波（39.4 / 58.8Hz）としてスペクトルに現れていました。512 / 19.68 ≒ 26 なので
「26 サンプルに 1 回、何かが起きている」ことになります。この2列はその「何か」の
正体を確かめるためのものです。

### 低周波のドリフトについて

窓ごとに**直線を当てはめて引いています**（平均を引くだけではありません）。平均だけ
だと窓の中の傾き＝電極のドリフトが残り、Hann 窓でも消えないので、脳波ではない
大きな 1〜5Hz の山として出てきます。実測でも、ヘッドセット自身の帯域分析が δ を
60% 前後で一定と言っている区間で、こちらのスペクトルの 1〜4Hz だけが 1/3 に落ちる、
という食い違いが出ていました。装着直後はまだ電極が落ち着いておらず本来の信号も
弱いので、この影響がいちばん強く出ます。

### 上限が 45Hz ではなく 64Hz な理由

商用電源のハム（50/60Hz）を**見るため**です。記録されたスペクトルは EEG らしく
減衰せず 45Hz の端に向かって上がり続けるものが多く、また曲線を乱して見せていた
12Hz と 38Hz のこぶは測定をまたいで連動し（r≈0.95）、足すと 50 になります。
帯域の外側にハムが居る典型的な兆候なので、そこまで届かせて直接確かめられるように
しました。**64Hz は診断用の帯域であって誘導に使える帯域ではありません**——
誘導周波数の入力上限は 45Hz のままです。

`spectrum` があるぶん CSV は従来の約 10 倍（15 分の測定で 0.7MB 程度）になります。
純 Python の DFT はビンが 45→64 に増えたぶん 4 割ほど重くなりますが、1 秒あたり
数十 ms のオーダーです。

## トラブルシューティング

| 症状 | 対処 |
|---|---|
| `ポートを開けません` | ヘッドセットの電源・ペアリングを確認。他のアプリ（公式アプリ等）がポートを使っていないか確認。ポート名を `--port COM4` のように指定して試す |
| signal が 200 のまま / 装着確認の警告 | 電極が額と耳にしっかり接触しているか確認（乾燥していると接触不良になりやすい） |
| 周波数スペクトルの形がおかしい（山が変な Hz に立つ・1/f の減衰にならない） | CSV の `specRate` 列を見る。測定中に動いていれば raw の取りこぼし（ヘッドセットとの距離・他の Bluetooth 機器・PC の負荷を確認）。安定しているのに形がおかしい場合は 50/60Hz のハムを疑い、45〜64Hz が盛り上がっていないか確認する（上記「CSV ログの列」参照） |
| `spectrum` 列が最初の数行だけ空 | 正常です。レートの中央値が取れるまでスペクトルを出しません |
| スマホ側が「ブリッジ：オフライン」のまま | ステップ A で切り分け。PC のネット接続、**スマホと PC で同じペアリングコードを使っているか**を確認（コードの大文字小文字・ハイフンは無視されます） |
| 送信失敗が連続する | 自動で再接続します。続く場合は `pip show realtime` でバージョンを確認（下記参照） |

## 既知の制約・技術メモ

- **realtime 送信ライブラリの成熟度**: Python から Supabase Realtime の
  broadcast 送信を行う API（`send_broadcast`）は JS 版より歴史が浅く、
  バージョンによりメソッド名が異なることがあります。問題がある場合は
  `pip install -U supabase` で更新してください。送信処理は `publisher.py` に
  分離してあるので、別の転送方式（DBテーブル経由など）への差し替えも容易です。
- **ThinkGear パーサー**: `thinkgear.py` は公開仕様（0xAA 0xAA 同期 +
  チェックサム + 0x83 = 8帯域パワー）に基づく自前実装です。万一お使いの
  ファームウェアで解析に問題がある場合は、公式の
  [Macrotellect/BrainLinkParser-Python](https://github.com/Macrotellect/BrainLinkParser-Python)
  を同梱（vendoring）して `main.py` の parser を差し替えてください。
- **チャンネルのアクセス制御**: 現状は「ペアリングコードを含むチャンネル名」による
  運用です（コードを知らない限り受信できませんが、厳密なアクセス制御では
  ありません）。本格運用時は Supabase Realtime の private channels + RLS の
  有効化を推奨します。
